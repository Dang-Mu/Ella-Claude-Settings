AI LANDSCAPE 수많은 AI 도구

하루가 다르게 늘어나는 AI 도구 — 다 좋아 보인다.

도구는 차고 넘친다

관통 메시지 문제는 "무엇을 쓸까" 가 아니라 "무엇을 위해 쓸까". 도구의 양이 부족했던 적은 없다.
03
VS 도구 vs 목표

도구 중심 · 목표 중심

도구 중심

지금 사용할 수 있는 도구 선택에 집중 하고, 지금의 자원으로 할 수 있는 일을 목표로 한다.

목표 중심

목표를 먼저 설정 하고, 도구를 역으로 설계 한다.

결정의 순서 도구가 답을 정하는 게 아니라, 목표가 도구를 정한다. 같은 도구로도 결과가 달라지는 이유.
04
DEFINITION 목표 기반 설계란?

목표 지점에 먼저 깃발을 꽂고, 거기까지의 경로를 역으로 설계.

Goal First vs Action First

GOAL FIRST

"어디로 갈지 정해!"

  • 목표 지점부터 결정
  • 경로는 역으로 설계
  • 도구는 마지막에 고른다
ACTION FIRST

"일단 시작해!"

  • 가진 도구로 출발
  • 방향은 시행착오로 잡는다
  • 목표는 사후에 맞춘다
05
WHY 목표 기반 설계란?

목표 설정이 설계 전체를 지배하는 이유

기준점
모든 결정의 기준
한정된 자원 사용의 효율성 증대. 기능 · 디자인 · 비용 · 시간 배분에 기준 을 세움.
단계 진행
Dev → Ops 까지
개발 완료 후에 운영 단계로 진행됨. 대부분 Dev 단계를 넘어서지 못하는 한계 를 극복.
AI 활용
AI 에는 목표가 필수
AI 는 명확한 목표 없이는 쓸모없음. 입력값이 애매하면 결과도 흐릿함.
06
CORE 목표 기반 설계란?

방향이 있는 가속 이 혁신을 만든다

방향이 없는 가속은 혼란이지만, 방향이 있는 가속은 혁신 을 만든다.
"내가 할 수 있는 것" VS "누가 겪는 문제를 해결하는 것"
07
BUSINESS 비즈니스적 관점에서의 목표

목표 = 시장의 선택 + 고객의 만족.

목표는 외부가 정해준다

구분의미
목표고객이 만족하는 상태, 시장에서 선택받는 상태
수단우리가 가진 기술 / 자원, 실현 가능한 방법
착각목표 = 출시 / 구현 성공이라고 오해하기 쉬움
  • 비즈니스에서의 '목표'는 단순히 기능을 완성하는 것이 아님
  • 고객이 느끼는 문제 해결 → 고객이 실제로 사용 → 비용을 지불하는 지점 = 목표
  • 목표는 내부가 아닌 외부 (시장과 고객) 가 정해준다
08
ACTION 목표 정의 3단계

불편 → 가치 → 지불

01 · FIND PAIN POINT
불편을 발견

누군가의 불편 을 해결한다. 모든 비즈니스의 출발점.

02 · CREATE VALUE
가치로 인식

그 해결이 고객에게 '가치'로 인식 된다.

03 · SHUT UP & TAKE MY MONEY
실제 지불

그 가치를 위해 돈이나 시간을 실제로 지불 한다.

검증 기준 세 단계가 모두 일어나야 비로소 비즈니스 목표가 달성된 것이다. 출시 자체는 목표가 아니다.
09
LIMIT 기존 접근 방식의 한계

자원 중심으로 시작하면 어디로 가는지 모른 채 달리게 된다.

"출시 자체" 가 목적이 되기 쉽다

  1. 보유 자원 중심의 시작 → "우리가 가진 건 무엇인가?"
  2. 수단에서 출발한 사고 → "이걸 어떻게 팔까?"
  3. 반복적인 시행착오 를 통한 개선
    희망편 → "우리가 가려고 한 곳이 여기였구나"  /   절망편 → "여긴 어디? 우린 누구?"
결과 '목표에 도달' 이 아니라 '출시 자체' 가 목적 이 되기 쉽다. 자원 낭비 위험이 크다 — 엉뚱한 기능 개발, 불필요한 투자.
10
NEW 새로운 접근 방식

결과 중심 → 과정 역설계 : '결정의 순서' 가 바뀐다.

수요 에서 출발하는 설계

01 · 문제 인식
불편 · 불만

누군가의 불편함, 불만, 비효율을 먼저 본다.

02 · 수요 확인
나만 겪나?

"이 문제, 나만 겪는 걸까?"

03 · 솔루션 컨셉
제품 / 서비스

문제에 적합한 컨셉을 구상하고 제품 · 서비스 형태 로 해결.

04 · 기술 활용
필요한 기술

가진 기술을 활용하거나 외부 기술 을 적용.

"내가 뭘 할 수 있을까?" 보다, "무엇이 해결되어야 할까?"

QUIZ 현대적인 API 방식

"지키지 않으면 당신은 해고!"

○○○○년, ○○○ (회사) 의 ○○ ○○○ (이름) 가 보낸 메일.

  1. 모든 팀은 서비스 인터페이스 로 데이터와 기능을 공개하세요.
  2. 팀들은 이 인터페이스로 통신 하세요.
  3. 직접 링킹, 다른 팀 저장소 직접 액세스, 공유 메모리, 백도어 등 다른 어떤 통신 방법도 허용되지 않습니다. 네트워크를 통한 서비스 인터페이스 호출만 허용합니다.
  4. 어떤 기술을 사용하는가는 중요하지 않습니다. HTTP, Corba, Pubsub, 커스텀 프로토콜 다 괜찮습니다.
  5. 모든 서비스 인터페이스는 예외 없이 외부에서 사용 가능 하도록 설계되어야 합니다.
  6. 이를 지키지 않는 사람은 해고될 것입니다.
  7. 고맙습니다. 좋은 하루 되세요!

ANSWER 현대적인 API 방식

2002년 아마존 의 제프 베조스

"Bezos API Mandate" — 모든 팀은 API 로만 통신한다.

왜 중요한가 이 한 통의 메일이 아마존 내부 시스템을 모두 API 로 바꿨다. 외부 공개도 자연스러워진다 — AWS 의 토대 가 된 결정.
"어떤 기술을 쓰든 좋다. 하지만 모두 인터페이스로만 통신 한다. 예외는 없다." — Jeff Bezos, 2002

PRACTICE 원하는 목표를 구체화하기

머릿속의 목표를 손에 잡히는 형태로 끌어내린다.

목표를 구체화 하는 4가지 방법

01 · BRAND
가상의 브랜드 설정
해결하고자 하는 '문제' 를 중심으로 브랜드 이름 · 로고 · 콘셉트를 정한다.
02 · PR ARTICLE
기사 작성
마치 이미 출시된 것처럼 작성. 실제 뉴스 기사처럼 자연스럽게.
03 · FAQ
FAQ 문서 작성
"이 서비스는 누구를 위한 건가요?" "어떤 방식으로 동작하나요?" 처음 보는 사람의 질문을 정리.
04 · LANDING
랜딩 페이지 구성
Canva · S3 정적 웹페이지 · EC2 호스팅 등으로 1페이지에 핵심 가치 를 보여준다.
